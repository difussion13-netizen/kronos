# Исследование: есть ли эдж у тейкера в конце окна (постановка и протокол)

Дата постановки: 2026-09-19. Инструмент: `analysis/takerprobe.py` (офлайн, stdlib,
данные — датасет `clobwin` + venue-кэш `markcalc`; торговый код не трогает).

## Зачем

Наши деньги теряются на стороне мейкера: медиана markout на платёж площадки
−12.62¢, среднее −11.29¢, все пять бинов калибровки отрицательны (блок K в
`markcalc.py`). Объяснение, выдвинутое в разговоре: в этом рынке зарабатывает не
прогноз, а **тайминг** — тейкер, который читает ленту оракула раньше, чем стакан
успевает уехать, и мейкер, который котирует оба берега на инвентарь-нейтральности
и жрёт рибейт. Если это так, то «войти тейкером по правильному критерию» — тот же
самый эдж, только доступный нам без модели. Значит надо измерить, а не обсуждать:
на каком шаге до конца окна, по какой цене и по какому критерию входа тейкер в
нашей истории выигрывал бы больше, чем стоит его вход.

## Что именно измеряется

Для каждого окна, по которому есть **платёж площадки** (`ptb`, `fp`, `y = fp ≥ ptb`),
и для каждого чекпоинта книги `cp ∈ {240,120,60,30,15,5,0}` секунд до конца окна:

* `t = end − cp` — момент решения;
* два кандидата в критерий:
  * **spot** — цена в `t`;
  * **twap** — среднее по *видимой* части разрешающего окна `[end−60, t]` (правило
    резолва = TWAP60 по gamma-метаданным рынка; при `cp > 60` разрешающее окно ещё
    не началось и twap вырождается в spot — это помечено в выводе);
* `gap = (цена/ptb − 1)·1e4` б.п. — «насколько ведущая сторона впереди страйка»;
* ведущая сторона = Up при `gap > 0`, иначе Down;
* **цена входа** = топ книги с того же чекпоинта: Up — по `ask`, Down — по `1 − bid`
  (книги комплементарны); `EV = (1 − p)` если сторона выиграла, `−p` если нет,
  минус тейкер-штраф `--fee-cents` (конвенция гейта M1: 0.5¢/акц).

Вывод строится из четырёх таблиц: детерминированность по `cp` (win% против цены и
«ошибка» = win% − цена — это и есть величина mispricing), сетки EV по `cp × |gap|`
и `cp × цена`, перебор `(cp, Δ, потолок цены)` с t-статистикой, плюс контроль
(та же книга, та же секунда, но взята *проигрывающая* сторона) и ёмкость-прокси
(оборот окна из clob-лога).

## Дисциплина против подглядывания

Информация — строго до `t`: берётся закрытие последней **закрывшейся** минуты
(именно так живёт движок: `spot = close(t−60)`) или последняя **закрытая** секунда
при `--secs-cache`. Вариант `naive` (минута, содержащая `t`) в выводе не участвует:
на `cp < 60` это подглядывание в разрешающий интервал. `ptb` и `y` берутся из
venue-кэша — платёж, а не наш клиновый прокси; иначе таблица меряла бы не то, за
что платят.

Свежий `clobwin` пишет на чекпоинтах ещё и отображённую глубину (`bs/as` — размер
на топе, `d2b/d2a` — суммарный объём в пределах 2¢), поэтому с `--inv-usd 500`
в Т4 появляется колонка «по объёму»: доля входов, куда $500 вообще влезает по
показанной цене. Для ТЕЙКЕРА это и есть исполнимость (он снимает показанный объём),
для мейкера — только верхняя граница (очереди нет). На старых датасетах колонок
нет → колонка честно печатается как «н/д», а не как 0%.

Разрешение — критично. Без 1-секундных клинов вопрос «последние 5 секунд»
**неизмерим**: минута старше точки входа на 60–120 с, т.е. мы смотрим на окно
глазами, у которых сама задержка больше того преимущества, которое ищем. Поэтому
в прогоне обязательны оба запуска: по минутам (весь набор, без сети) и на 1с-клинах
(докачка с `api.binance.com`, кэш `/tmp/kl1s.jsonl`, ~1 запрос на окно).

## Критерии, которыми верим результату

1. `n ≥ 20` **окон** (не входов — входы внутри окна скоррелированы) и `|z| ≥ 2` по
   среднему EV; ячейки с `Δ < 2` б.п. не читаем вовсе — это внутри шума
   «Chainlink против Binance» (медиана 0.81 б.п. в метку времени, p90 1.85).
2. Сетка Δ сравнивается **внутри актива** (`--split-asset`): σ окна у sol/xrp в
   2–3 раза больше, чем у btc, и «5 б.п.» для них — разная ставка (урок 3 из
   `measured-signal-baseline.md`).
3. Знак EV обязан держаться **во все сутки** выборки; «в большинстве» — не результат.
4. Тейкер платитspread'ом, которого в наших числах нет: цена = топ книги на 1
   акцию, без глубины и без очереди. Это **верхняя** граница. Реальное сравнение с
   нашим мейкерским минусом (−11.29¢) корректно только после проверки ёмкости:
   если медианный оборот окна $2k, а вход $15 — это 0.7% рынка и на таком объёме
   «взять топ» правдоподобен, но «взять 500$» уже нет.
5. Никакого cherry-picking по `cp`: если эдж виден только на `cp = 0` — это не эдж,
   а наша неспособность исполнить заявку в последнюю секунду (CLOB + Polygon +
   гео-блокировки), и проверяется это только live-замером (M6/M7), не реплеем.

## Сутки, которые берём

Рваные сутки 15–16.09 вычеркнуты заранее (по ним мы не считаем ничего — урок 17.09:
«за 15 число у нас битые данные, используй хорошие»). Рабочий набор: **20260904–
20260914 + 20260917–20260918**. Но у исследования есть жёсткое условие поисточнику:
нужны **книги CLOB**, а поток `clob` в логгере появился позже, чем binance/rtds.
Поэтому первым делом — какие сутки вообще пригодны:

```bash
aws s3 ls s3://kronolog-moi1234/kronolog/clob/ | awk '{print $2}' | tr -d : | sort -u
aws s3 ls s3://kronolog-moi1234/kronolog/binance/ | awk '{print $2}' | tr -d : | sort -u | tail -3
```

Если первая строка начинается с 2026-09-14 — набор исследования = `20260914,20260917-20260918`
(~3.4k окон, этого хватает на Т1 и Т4 по btc/eth, но НЕ на устойчивые выводы по
sol/xrp и не на «знак во все сутки» — это надо писать в выводе открытым).

## Платёж по ВСЕМ окнам (новая опция markcalc)

Venue-кэш раньше наполнялся только по рынкам из нашего журнала: для суток до 16.09
журнала нет ⇒ платёжа нет ⇒ `takerprobe` видел бы скошенный набор. Для этого в
`markcalc.py` добавлен отдельный режим — он ничего не считает, только доканчивает
`priceToBeat/finalPrice` по списку ключей (файл `asset,start` или каталог/файл
`windows_*.csv`), пишет в тот же `--venue-cache` и умеет параллельные запросы:

```bash
python3 /tmp/markcalc.py --venue-keys /tmp/win --venue-key-codes 5m \
  --venue-key-days 20260914,20260917-20260918 --venue-workers 6 --venue-cache /tmp/venue.jsonl
```

Ритуальный прогон (без `--venue-keys`) не изменился: `--venue-workers` по умолчанию 1,
последовательный опрос с pacing — лимиты Cloudflare трогаем только явно.

## Ядра и диск (почему 6, и почему диска почти не надо)

* **clobwin** — единственная тяжёлая часть: два прохода по 8.8 ГБ/сутки clob-лога.
  Распараллелен по суткам (`--jobs 6`: на 6 ядер это 13 суток = 3 волны ≈ 40–60 мин,
  из них ~5–15 мин CPU на ядро-сутки). Файл на диск пишет только результат —
  `windows_{day}.csv` (~0.4 МБ/сутки) и `minutes_{day}.csv` (~0.2 МБ/сутки).
* **Платёж (gamma)** и **1-секундные клины (Binance)** — сетевые, не CPU: поэтому в
  `takerprobe` докачка 1с-клинов идёт пулом `--workers 6` с общим ограничителем
  `--rate 45` запросов/с (вес 1с-клина = 2, лимит 6000/мин ⇒ потолок ~50/с; за
  превышение банят IP). 3.4k окон = ~1.5 мин вместо ~6 мин последовательно.
* **Само построение строк и таблицы** — ~10 с на одном ядре на 3.4k окон; множить
  ядра тут не на что (pickle дороже работы), поэтому `--jobs` в takerprobe нет
  сознательно: параллелить надо сеть и clobwin.
* **Диск**: 13 суток датасета ≈ 8 МБ, кэш 1с-клинов ≈ 45 МБ (300 чисел × ~3.4–15k
  окон), venue-кэш ≈ 2 МБ, `kl5` (минутки Binance для markcalc) ≈ 10 МБ. Итого
  **< 100 МБ**, плюс запас на временные файлы и `tee`-логи: **нужно ~1 ГБ свободно
  на /tmp**. Лог в S3 на диск НЕ скачивается — `aws s3 cp - | zcat` идёт трубой,
  и это единственная причина, по которой расчёт тяжёлый, а не диск. Проверка и
  калибровка одной командой:

```bash
df -h /tmp / | sed -n '1,4p'; du -sh /tmp/* 2>/dev/null | sort -h | tail -5
python3 /tmp/clobwin.py --bucket kronolog-moi1234 --day 20260918 --outdir /tmp/win1 --minutes
du -sh /tmp/win1   # ×число суток = потолок датасета; у нас это единицы МБ
```

## Команды прогона

Всё ниже собрано в `scripts/run-calc-studies.sh` (идемпотентен, шаги помечены
файлами-маркерами, при отказе сети шаг 1с НЕ считается выполненным) — на калькуляторе
достаточно:

```bash
cd /tmp && curl -sL -O https://raw.githubusercontent.com/difussion13-netizen/kronos/arena/01a063d9-kronos/scripts/run-calc-studies.sh
nohup bash /tmp/run-calc-studies.sh > /tmp/run.log 2>&1 &     # ~25–60 мин на 3 сутки
tail -f /tmp/run.log
```

Ручная последовательность приведена далее — она остаётся источником правды, если
скрипт придётся обходить (например `DAYS=` или `STEPS=` не покрывают случай).

Первым идёт шаг `sync`: он берёт **готовый** датасет из `s3://…/kronos/win/`
(на 20.09 там окна и минутки за 03–14.09, ~200 КБ на сутки) и помечает `clobwin`
выполненным. Стройка нужна только для суток, которых в снапшоте нет, и у снапшота
есть одно известное ограничение: он построен до 19.09, то есть без колонок
`d2b*/d2a*`. Тейкер из-за этого печатает «по объёму = н/д» (ЁМКОСТЬ по глубине
стакана требует пересборки с `--depth-cents`), а MM-симу хватает: его фильтр участия
меряется по `vol_usd`, а не по глубине.

## Команды вручную (калькулятор, 6 ядер; шаги 2–3 — самые долгие, держать в tmux)

```bash
mkdir -p /tmp/kronos && cd /tmp/kronos
for f in clobwin takerprobe markcalc; do
  curl -sL -o /tmp/$f.py https://raw.githubusercontent.com/difussion13-netizen/kronos/arena/01a063d9-kronos/analysis/$f.py
done
python3 -m py_compile /tmp/clobwin.py /tmp/takerprobe.py /tmp/markcalc.py \
  && python3 /tmp/takerprobe.py --selftest

# 1) сутки с книгами (см. выше) — задать DAYS явно
DAYS=20260914,20260917-20260918
# 2) датасет «окно→книга» + минутки, 6 ядер: параллельно по суткам
python3 /tmp/clobwin.py --bucket kronolog-moi1234 --days $DAYS --outdir /tmp/win \
  --minutes --jobs 6 --gamma-threads 12 --map-s3 kronos/win/tokens_map.json
# 3) платёж площадки по ВСЕМ окнам этих суток
python3 /tmp/markcalc.py --venue-keys /tmp/win --venue-key-codes 5m --venue-workers 6 \
  --venue-cache /tmp/venue.jsonl
# 4) исследование: по минутам (весь набор, сети не требует)
python3 /tmp/takerprobe.py --win /tmp/win --venue /tmp/venue.jsonl --code 5m \
  --days $DAYS --split-asset --min-n 20 2>&1 | tee /tmp/taker-min.txt
# 5) то же на 1-секундном разрешении (докачка 1s-клинов, кэш остаётся)
python3 /tmp/takerprobe.py --win /tmp/win --venue /tmp/venue.jsonl --code 5m \
  --days $DAYS --split-asset --min-n 20 --secs-cache /tmp/kl1s.jsonl \
  --workers 6 --rate 45 --max-windows 1500 2>&1 | tee /tmp/taker-1s.txt
```

Если `--max-windows 1500` не покрывает весь набор (в выводе видно «докачать N»),
повтори шаг 5 с бо́льшим числом: кэш дополняется, а не перекачивается. Если расчёт
делается НЕ на боксе логгера, а на отдельном калькуляторе — `kl5`/`venue.jsonl`
лежат в `/tmp` того бокса, где стоял трейдер; перегонять их через S3 не нужно,
кроме `venue.jsonl` (его мы пересоздаём шагом 3, это дешевле пересылки).
