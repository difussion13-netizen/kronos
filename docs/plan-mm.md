# MM-фаза: бумажный симулятор котировок со скью (гейты зафиксированы заранее)

Контекст: E1–E4 закрыты (docs/plan-4-evals.md «Результаты»): пай есть, наивный
пассив — донор (markout −26.5¢), якорь Φ(Δ/(σ√τ)) бьёт рынок 11/11 дней, σ-слой
OLS даёт +80%. Вопрос фазы один: **превращается ли статистическое превосходство
якоря в положительный P&L двустороннего котирования с инвентарной логикой**.
Торговли нет; это симуляция на уже собранных датасетах (запрет юзера в силе).

## Модель (upper-bound по исполнению)

* Точки решений — чекпоинты книг: 5m: c∈{240,120,60}¢ (следующая проверка
  исполнения — на c−120: 120,60,30), 15m: {600,240,120,60}. Последние ~30 с
  не котируем (fill-ловушка «финального бегуна»).
* Центр котировки: pa = Φ(Δ/(σ·√(τ/300))), Δ — отклонение Binance-цены от
  бенчмарка окна, σ — std 120-мин log-returns (fallback) или volat12 из /tmp/ds.
  **Информация строго до t решения** (урок E3: минуты берутся с лагом 60 с).
* Полуширина: h = max(0.5¢, k·φ(x)·√(шаг/τ)) — ширина ∝ одного шага неопределённости
  вероятности; k первичный = 2.5 (sweep 1.5/2.5/4.0 — для робастности, не для выбора).
* Исполнение по касанию с пессимизмом: fill, если mid на следующем чекпоинте
  пересёк наш уровень больше чем на f=0.5¢ (sweep 0/0.5/1.0). Очередей/глубины
  у нас нет — P&L остаётся ВЕРХНЕЙ границей.
* Инвентарь: позиция одна, |pos|≤1 share; держим YES → котируем только offer;
  держим NO (купили 1−ask) → только bid; слияние YES+NO=$1 (пара) = выход;
  иначе резолв y=1[fin≥bench] (тай→Up). Рибейт 0.2·0.0625·p(1−p) на каждую
  maker-ногу (как в clobzero).
* Нейтральный контроль (центр=mid рынка, та же ширина) — запуск той же функции
  с `--anchor off`; разница по дням и есть тест якоря (G3), а не «spread capture».

## Гейты (первичная конфигурация k=2.5, f=0.5¢, anchor on; решают фазу)

* **M1**: медианный дневной P&L > 0 и ≥70% дней положительны;
* **M2**: медиана markout позиций, дотащённых до резолва, > −0.5¢ (то же
  сито, что завалило E2-наивных: −26.5¢ → скью обязан отжать);
* **M3**: P&L(anchor) − P&L(neutral) > 0 на ≥⌈2/3⌉ дней (якорь даёт прибавку,
  а не просто мы ловим спред);
* **M4** (робастность): P&L > 0 хотя бы в 2 из 3 k и 2 из 3 f сетки (никакого
  cherry-pick: отчёт по всей сетке публикуется).
Два и более «нет» → MM-направление закрываем с протоколом (данные E1–E4
остаются в репо). «Да» при M1–M3 → следующий артефакт — не торговля, а
«production-candidate»: модель очереди + оценкаRequired глубины + симулятор на
полных сутках (14+ дней), и только потом разговор о live (ToS-решение юзера,
BY=close-only).

## Запуск

    # машина с доступом к S3 (CloudShell хватит: файлов ~10 МБ, без Gamma)
    curl -sL -o /tmp/clobmm.py \
      "https://raw.githubusercontent.com/difussion13-netizen/kronos/arena/01a063d9-kronos/analysis/clobmm.py?nc={NC}"
    mkdir -p /tmp/win && aws s3 sync s3://kronolog-moi1234/kronos/win /tmp/win
    python3 /tmp/clobmm.py --win /tmp/win --compare --sweep

Выход: таблица primary (fills/pairs/P&L/markout/дни) × {anchor,neutral}, сетка
sweep, вердикты M1–M4, json-сводка `/tmp/win/mm_summary.json`.

## Результаты MM-01 (15.09.2026, реальные данные 20260903–20260913, 15 611 окон)

Первичная конфигурация (зафиксирована ДО прогона: k=2.5, f=0.5¢, anchor on):

    primary  fills 2209  pairs 30  singl 2179  P&L +40 566$  дни+ 11/12  markout_med +7.84¢
    control  fills 1586  pairs 105 singl 1481  P&L  -6 071$  дни+  1/11  markout_med −11.21¢
    разница по дням (якорь−нейтраль): 11/12 в плюс, медиана +2 037$/день

Сетка робастности (все 9 ячеек P&L>0; +19.4k$ минимум при k=4/f=1¢, +75.3k$ максимум при
k=1.5/f=0¢; медиана markout от −7.6¢ при k=1.5 до +14.1¢ при k=2.5/f=1¢).

Вердикты: **M1 ДА, M2 ДА, M3 ДА (11/12), M4 ДА** — все четыре, при том что первичный k —
не максимум сетки. Направление ММ подтверждено на бумажной модели: скью якоря переворачивает
E2-донорство (+7.8¢ медиана против −26.5¢ у наивного пассива) и даёт положительный P&L
верхней границы ~$3.4k/сутки при сайзе 100 shares (~$5k неional на окно в среднем…
позиция ≤100 shares на окно).

Чего это ЕЩЁ не значит (зарегистрировано заранее, не задним числом):
1. исполнение по касанию — без очерёдей и частичек: реальный P&L ниже этой границы
   (на сколько — покажет только модель очереди на данных с глубиной);
2. период 11 суток = один режим рынка; нужна реплика на свежих сутках (09/14–20+) ДО
   любых выводов о capacity/ожидаемой доходности;
3. резолв-ярлык — наш Binance-прокси (fin≥bench по минутам), не настоящий CL-TWAP:
   систематика хвостов может отличаться;
4. это не торговый код и не приглашение к торговле: вопрос live по-прежнему упирается
   в ToS-решение владельца и юрисдикцию (BY = close-only).

Следующие артефакты (по плану фазы): (A) реплика периода — clobwin на 20260914–20260920
(карта токенов в S3, passA только по новым суткам, ~25 мин на c6i.2xlarge), затем
clobmm на всём окне 03–20; (B) апгрейд логгера: писать топ-5 уровней книги и timestamp
каждого fill-события рядом с our-quote-уровнем (kronolog правка, только будущие данные),
— из него строится модель очереди; (C) после (A)+(B): честная оценка P&L с множителем
исполнения и capacity по reward-пулу.

## Админкулатура 15.09 (M5, реплика)

Первая попытка реплики дала нули по двум причинам: (1) clobwin пропускал passA новых
суток при готовой карте — исправлен (per-day coverage, bec12b8, фикстурный тест);
(2) суток 15+ ещё не существовало (логгер жив: 14.09 записан полностью, 70.2M строк;
«8 окон» на 14-м — это 4h-окна 13.09 через полночь, сверка сошлась). M5 = P&L>0 и
markout>−0.5¢ на свежих сутки: прогон по 14.09 — смоук-тест конвейера, финальный вердикт
— когда накопится ≥7 новых дней (14–20.09) и выше. Карта-покрытие синхронизируется
через S3 (tokens_map.json + .days), инкремент с сервера-логгера не нужен.

## Смоук 14.09 (после фикса per-day coverage)
