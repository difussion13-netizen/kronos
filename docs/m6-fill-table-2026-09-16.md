объёмом + x лотов.

## Выводы, фиксированные для M6/M7

1. Fill-on-touch (модель clobmm/smoke 14.09) завышает частоту исполнений на
   порядок: реалистичный множитель для +100 лотов на t−4min ≈ 0.02–0.03 от
   touch-события, у конца окна ≈ 0.001. Любой будущий «+N $/день» умножается
   на это — M5-гейт остаётся мерой ЦЕНЫ (есть ли edge на касании), M6/M7 —
   мерой ДОСТУПНОСТИ (дойдёт ли объём).
2. Видимая глубина best ≈ $20–25 на сторону — capacity на заявку $50–100
   строится из ~2к «полных съеданий» уровней в сутки (0.098×20676) при
   5m-мире: порядок — сотни исполнений/день, не тысячи.
3. Очерёдность потоков: 5m/15m = оборачиваемость через touch+consumption,
   4h = «last-minute adverse» — модель должна иметь разные fill-ораклы по
   сериям, единая таблица вводит в заблуждение.
4. clobcap.py (после M5 на финальном датасете 14–20.09): policy из clobmm ×
   эта таблица как p_fill, net $/сутки по сетке (k, f, size), сплит 60/40 по
   дням; пред-гейт M6 «capacity при честной очереди > 0 с запасом ≥20%» —
   считается именно здесь.

Ожидаемый ИСПОЛНЕННЫЙ оборот `E[min(x, traded−s_at)]·price`, ранг0, $/сутки

Holdout-значения ниже на 20–25% (5m x100: 8 448 против 10 684).

Вербатим гейтов:
- **Устойчивость оракла (x=100, Σcp, train→holdout): 5m −19% (гейт <30% ПРОЙДЕН),
  15m −39% (погранично), 4h −154% (оракл бесполезен — n окон не даёт оценки).**
  → capacity-модель строится на 5m (+15m как тень), **4h исключается из
  fill-capacity** — там и так только adverse last-minute поток.
- **Ёмкость: не лимитирующий фактор.** Даже консервативная «хвост за
  существующим best» даёт ~$10k/сут исполняемого оборота на ранний чекпоинт
  5m при x=100 — на порядки больше M10-M12 потребностей; кривая x→$/сут
  сублинейна (x8 → ×2.7 оборота), т.е. рост размера платит падением
  fill-эффективности, не упирается в объём.
- Разброс по дням 5m: 53.5k–123k $/сут (2.3×) — объём рынка сам скачет;
  M7-гейт «худший день» считать по P&L-дням, не по дням объёма.

Кавэат, зафиксированный честно: (a) Σ по cp суммирует взаимно-пересекающиеся
сценарии «пришёл в момент cp» — для одной заявки, стоящей с t−240, верна
строка cp=240, не Σ; (b) traded меряется по всему окну, поэтому часть
посчитанного оборота случилась ДО момента чекпоинта и наша заявка её не взяла
бы (для 5m cp=240 — до ~20% окна, для 4h cp=240 — доли процента): строки
ранних cp смещены вверх на эту долю; (c) ранг2 и off-book/price-improvement
размещения — вне модели (эффект снизу).
Вердикт M6 «capacity>0 с запасом» выполняется на этом датасете с огромным
запасом; финальная цифра — на 14–20.09 после M5, умножением на edge-на-fill.
